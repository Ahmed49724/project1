# Parent + Secure Auth Foundation Design

## Goal

Build the first production-grade foundation for Jamea as a bilingual homeschooling platform: one account owner, safe child sub-accounts, role-based access, and a clean session model that works across the main platform and the Verb Lab without asking the child to log in twice.

This phase intentionally does not build the full teacher dashboard, billing, live classes, or marketplace. It creates the account and permission layer those features depend on.

## Current Project Context

The active production surface is currently the root Vite/static app:

- `index.html` contains the platform shell, login overlay, Arabic journey, and embedded learning sections.
- `src/scripts/main.js` owns the current login, progress loading/saving, navigation, and iframe session bridge.
- `src/scripts/verb-lab.js` owns the standalone Verb Lab experience and already accepts a parent-platform session when embedded.
- Supabase is currently used directly from the browser for progress storage.
- Google sign-in exists in UI/code but is disabled until the provider is enabled in Supabase.
- `frontend/` and `backend/` exist, but the Next.js and NestJS apps are still early scaffold code and should not become the primary runtime in this phase.

## Product Decision

The first MVP slice is the Parent + Secure Auth Foundation.

Priority order:

1. Parent account owner and authentication.
2. Child sub-accounts controlled by the parent.
3. Student access by child code or PIN, not personal email/password.
4. Shared session bridge for the main platform and Verb Lab.
5. Role-based UI gates for parent, student, teacher, and admin.

## User Roles

Parent:

- Owns the billing/legal account.
- Creates and manages child profiles.
- Approves course access for each child.
- Can view progress and weekly summaries.

Student:

- Has no personal email login in this phase.
- Enters with a child code or PIN generated by the parent.
- Sees only the learner interface and assigned content.
- Can enter Verb Lab without a second login once launched from the platform.

Teacher:

- Exists as a reserved role in the data model.
- Can be added later without changing the core auth model.
- No teacher dashboard is implemented in this phase.

Admin:

- Exists as a reserved role for future account support and compliance operations.
- No admin UI is implemented in this phase.

## Authentication Model

Recommended model for this phase:

- Parent signs in using email magic link first.
- Google sign-in remains hidden unless enabled and verified in Supabase.
- Parent creates child profiles after sign-in.
- Each child profile receives a generated short access code, plus an optional PIN.
- Student mode starts when a valid child access code is entered.

Why not full Google-only auth now:

- The current Supabase project is not configured for Google OAuth.
- The user already hit `Unsupported provider: provider is not enabled`.
- Email magic link and student code are lower-risk and can run immediately.

## Data Model

Core tables:

`profiles`

- `id` UUID, primary key, linked to auth user where applicable.
- `email` text, nullable for child profiles.
- `display_name` text.
- `role` enum: `parent`, `student`, `teacher`, `admin`.
- `created_at` timestamp.

`parent_children`

- `id` UUID.
- `parent_profile_id` UUID.
- `child_profile_id` UUID.
- `relationship_label` text, such as `mother`, `father`, `guardian`.
- Unique pair: parent + child.

`child_access_codes`

- `id` UUID.
- `child_profile_id` UUID.
- `code_hash` text.
- `pin_hash` text, nullable.
- `expires_at` timestamp, nullable.
- `revoked_at` timestamp, nullable.
- `created_at` timestamp.

`student_progress`

- Existing concept should be retained.
- It should move from `student_code` as identity to `child_profile_id` as the durable owner.
- Keep `student_code` temporarily as a migration/fallback field.

`course_approvals`

- `id` UUID.
- `parent_profile_id` UUID.
- `child_profile_id` UUID.
- `course_id` text.
- `status` enum: `approved`, `blocked`, `pending`.
- `created_at` timestamp.
- `updated_at` timestamp.

## Session Shape

The app should normalize all login methods into one client-side session object:

```json
{
  "sessionType": "parent" ,
  "profileId": "uuid",
  "role": "parent",
  "displayName": "Parent Name",
  "activeChildId": "uuid-or-null",
  "activeChildName": "Child Name",
  "language": "ar",
  "theme": "light"
}
```

Student mode session:

```json
{
  "sessionType": "student",
  "profileId": "child-uuid",
  "role": "student",
  "displayName": "Student Name",
  "activeChildId": "child-uuid",
  "activeChildName": "Student Name",
  "language": "ar",
  "theme": "light"
}
```

This replaces scattered globals over time, while keeping compatibility with the current `window.studentCode`, `window.studentEmail`, and Verb Lab bridge during migration.

## UI Flow

Login overlay:

- Title stays platform-level, not Verb Lab-specific.
- Parent sign-in is the primary path.
- Student code access is the secondary path.
- Google button is hidden unless Supabase Google OAuth is enabled and tested.
- Arabic/English toggle remains available before login.

Parent first-run flow:

1. Parent signs in by email.
2. Parent sees a minimal child setup screen.
3. Parent adds child display name and optional age/level.
4. System generates a child access code.
5. Parent can enter student mode for that child.

Student returning flow:

1. Student enters code/PIN.
2. System resolves the child profile.
3. Platform opens directly to the student learning shell.
4. Verb Lab receives the same child session if opened from the platform.

## Verb Lab Integration

Verb Lab remains a separate file internally for maintainability, but it behaves as one website to the user.

Required behavior:

- If embedded from the main platform, Verb Lab hides its internal login and top-level account controls.
- It receives `activeChildId`, child display name, language, theme, and progress from the parent platform.
- It sends progress updates back to the parent platform through `postMessage`.
- If opened standalone, it may still show a fallback login, but this is not the default user journey.

## Security Rules

Frontend rules:

- Never expose a child name, email, or code in a URL.
- Never store raw PINs or access codes in localStorage.
- Keep temporary local progress fallback, but sync against `child_profile_id` when available.
- Do not show teacher/admin controls based only on localStorage flags.

Backend/database rules:

- Enable row-level security on all account and progress tables.
- Parent can read/write only their own profile and linked children.
- Student can read/write only their own progress.
- Child access code verification must compare hashes, not raw stored codes.
- Course approvals must require a parent profile.

Compliance baseline:

- Parent consent is required before creating child profiles.
- Child profiles should store minimal personal information.
- Audit events should be added for account creation, child creation, code regeneration, and course approval.

## Error Handling

Login:

- If Google is not enabled, hide the button instead of letting users hit Supabase provider errors.
- If email sign-in fails, show a short user-safe message and log detailed diagnostics to console only in development.
- If a student code is invalid, say the code could not be found without revealing whether a child exists.

Progress:

- If Supabase is unavailable, use local progress fallback and show no blocking error to the child.
- When sync returns, merge local progress into remote progress by completed item IDs and highest star count.

Embedding:

- If Verb Lab does not acknowledge the session within a timeout, show a retry action on the parent platform.
- Do not ask the student to log in again when embedded.

## Migration Plan

Step 1:

- Keep the existing Vite/static app as the shipping surface.
- Add a small auth/session module in `src/scripts/main.js` or a new `src/scripts/auth-session.js`.
- Preserve existing global function names used by inline HTML, such as `loginStudent()`.

Step 2:

- Add Supabase tables and RLS policies.
- Move progress ownership toward `child_profile_id`.
- Keep compatibility with existing `student_code` records.

Step 3:

- Add parent mode UI inside the current platform shell.
- Add child creation and child switcher.

Step 4:

- Update Verb Lab bridge to prefer `activeChildId`.
- Keep `studentCode` fallback until old saved progress is migrated.

Step 5:

- Later, move the same account model into the Next.js/NestJS app when the platform is ready for a full framework migration.

## Testing Plan

Manual tests:

- Parent can sign in with email and does not see Google unless enabled.
- Parent can create a child profile.
- Child can enter with generated code/PIN.
- Student mode opens Arabic journey.
- Verb Lab opens from the platform without another login.
- Language toggle works before and after login.
- Logout clears only the current browser session, not remote progress.

Automated checks:

- JavaScript parse check for `src/scripts/main.js`, `src/scripts/i18n.js`, and `src/scripts/verb-lab.js`.
- Build check with `npm run build`.
- Session shape unit tests once auth/session logic is separated.
- Supabase RLS tests before production use.

## Out Of Scope

- Teacher course builder.
- Mass grading.
- Live video classrooms.
- Billing/subscriptions.
- Portfolio PDF export.
- Full Next.js/NestJS migration.
- Google OAuth setup inside Supabase dashboard.

## Open Implementation Choices

Recommended defaults:

- Use Supabase Auth for parent email magic link now.
- Use Supabase Postgres tables with RLS for profiles, children, progress, and approvals.
- Use hashed child codes/PINs for student access.
- Keep the current static app until this foundation is stable.

Deferred choices:

- Whether to adopt Auth0 later depends on budget, compliance requirements, and whether Supabase Auth becomes limiting.
- Whether to migrate to Next.js/NestJS should be decided after the core student/parent flows are stable.
